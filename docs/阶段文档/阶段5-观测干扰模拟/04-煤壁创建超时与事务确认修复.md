# 煤壁创建超时与事务确认修复

## 已核实的问题

用户第二次 GUI 运行 `/tmp/hydromining_phase5_gui_v2` 在重放 UPDATING 阶段报 `create failed: Service call timed out`。聚合 RSS 峰值为 2579.707 MiB，低于 3072 MiB，故这次不是内存保护触发。Gazebo 日志还出现 `NodeShared::RecvSrvRequest() error sending response: Host unreachable`。

旧适配器每次 RPC 等待 5 秒，未收到创建回执即报错；超时不代表操作未执行。若候选煤壁已经创建，旧逻辑可能既返回失败又留下新显示网格，数值状态仍未提交。原 GUI 日志未记录最终场景快照，不能追溯确定这次超时后模型最终是否生成，也未独立定位传输延迟的底层原因。

同一运行另有控制器启动 RPC 10 秒等待超时后重发，随后收到“已经 active”的错误；机械臂最终成功运行，故不是此次重放中断的直接原因。现将调用等待设为 40 秒，覆盖原有 30 秒切换等待，减少在切换尚未结束时重发。

## 修复后的规则

1. `coal_wall_scene` 使用已安装的 Harmonic C++ Transport/Msgs 对场景进行只读查询，将官方 protobuf 转为 JSON；Python 无需额外 Gazebo 绑定。ROS 层通过包索引传入安装路径，支持 `--symlink-install`。
2. 对模型名进行精确匹配，确认目标 visual 的实际网格 URI；不能只以“存在 coal_wall 名字”为成功。
3. 删除与创建回执丢失时，先轮询实际状态。创建等待为 10 秒、确认窗口 6 秒；读查询和进程等待也均有上限。
4. 只有核实目标不存在，才允许一次有界重发；始终 `allow_renaming: false`。场景不可查询或存在错误网格时，不能盲目重发。
5. 只有确认新网格才允许提交数值状态。无法确认则标记失同步，阻止下一次喷射，成功重置后恢复；取消旧的盲目回滚，以免与延迟创建冲突。

该确认针对场景模型与 visual 网格。`scene/info` 实测不包含 collision 几何，不能把此结果称为独立碰撞接触验证；visual/collision 仍由同一个 SDF 使用相同 URI 创建。

设计参考 [Gazebo Harmonic 官方实体创建说明](https://gazebosim.org/api/sim/8/entity_creation.html)：操作执行、服务返回结果和请求超时是不同状态；关闭自动重命名可避免同名实体被自动复制。
